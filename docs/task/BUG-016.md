# BUG-016 删光构建物后版本显示 Unknown platform / architecture

- **status**: completed
- **priority**: P2
- **owner**: Claude
- **createdAt**: 2026-06-28

## 描述

在 Dashboard 删除某个版本下的（最后一个）构建物后，该版本记录在列表里变成一条 `Unknown platform / Unknown architecture` 的空白条目，而不是显示为“没有构建物”。

## 根因

删除链路本身正确：`/artifact/delete` 用读-改-写把 `apps` 文档的 `artifacts` 数组删成干净的空数组 `[]`（已在 vm-node02 直查确认 raw 数据为 `artifacts: []`）。

问题在展示接口 `/search`（`GetAppByName` → `getBasePipeline`，`server/mongod/structs.go`）。其聚合 pipeline 对空 artifacts 的处理有缺陷：

1. `$unwind {path:"$artifacts", preserveNullAndEmptyArrays:true}`：空数组保留文档，但 `artifacts` 字段变为缺失。
2. `$addFields {"artifacts.platform": ..., "artifacts.arch": ...}`：对缺失的 `artifacts` 做点路径赋值，MongoDB 凭空创建出一个空对象 `{}`。
3. `$group {artifacts: {$push: "$artifacts"}}`：把这个 `{}` 塞回数组 → `artifacts: [{}]`。

前端拿到 `[{}]`，`artifact.platform || 'Unknown platform'`、`artifact.arch || 'Unknown architecture'` 即 fallback 成 Unknown。任何 artifacts 为空的版本都会触发，与删除操作无关。

vm-node02 真实数据复现：raw `artifacts: []` 经原 pipeline 输出 `artifacts: [{}]`。

## 修复

在 `getBasePipeline` 的 `$group` 之后追加一个 `$filter`，按 `link` 是否存在剔除幽灵空对象（真实 artifact 必有 S3 `link`，幽灵 `{}` 没有）：

```
$addFields: { artifacts: { $filter: {
  input: "$artifacts", as: "artifact",
  cond: { $ne: [ { $type: "$$artifact.link" }, "missing" ] }
}}}
```

空版本正确返回 `artifacts: []`，有构建物的版本完全不受影响。`getBasePipeline` 被 `check.go` 多处复用（搜索/版本检查），过滤幽灵条目对所有调用方都正确。

## 验证

- 本地 `go build` / `go vet` / `go test -count=1 ./mongod/... ./server/handler/...` 全绿。
- 新增护栏测试 `server/mongod/pipeline_test.go::TestGetBasePipelineFiltersGhostArtifacts`，防止 `$filter` 被回退（可本地运行）。
- vm-node02 真实数据实测修复后 pipeline：空版本 `6a204cc9`→`artifacts: []`；满版本 `6a204bfc`→3 个构建物原样保留并正确解析平台/架构名称。
- 行为正确性的端到端断言依赖根包集成测试（需 Mongo/S3/Redis），本地不可运行；CI 仅做编译门。已用真实数据实测 + 部署后冒烟替代。
