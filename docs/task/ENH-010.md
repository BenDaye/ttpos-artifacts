# ENH-010: 为元数据模型引入持久化 Sort 排序与 Dashboard 拖拽

- **status**: completed
- **priority**: P2
- **owner**: ben
- **createdAt**: 2026-06-01
- **completedAt**: 2026-06-01
- **related**: SEC-007

## 描述

App / Channel / Platform / Arch 四个 owner 维度元数据列表此前没有任何排序概念，展示顺序取决于插入/`_id` 顺序，用户无法自定义。本任务为这四类引入一个持久化的 `Sort` 字段，并在 Dashboard 提供拖拽排序，让每个 owner 能自定义这些实体的显示顺序。

## 方案

采用**自愈式 dense-integer**（无独立数据迁移）：

- `Sort` 按 **(owner, type)** 作用域。四类同住 `apps_meta` collection，靠判别字段区分（`channel_name` / `platform_name` / `arch_id` / `app_name`），绝不取全局 max，避免四类交错。
- 读取：列表查询统一按 `{sort:1, _id:1}` 升序。老文档没有 `sort` 字段，Mongo 升序里 null/缺失排在数字之前，因此存量维持当前创建顺序，直到第一次拖拽。
- 新建：在创建收口按 (owner, type) 取现有 `sort` 最大值 +1（无则 0），追加到末尾。
- 重排：每类一个 `POST /{type}/reorder` 端点，前端传**完整有序 ID 列表**，后端校验全部属于该 owner+type 后用 bulkWrite 重写 `sort = 0..N-1`。复用既有 `CheckPermission(PermissionEdit, Resource{Type})`，不新造权限。

## 范围

### Server
- `server/server/model/model.go`：App/Channel/Platform/Arch 各加 `Sort int`（`bson:"sort" json:"Sort"`）。
- `server/mongod/list.go`：`listItems`（四列表唯一收口）加 `SetSort({sort:1,_id:1})`。
- `server/mongod/create.go`：`createMetaDocument` 注入按 (owner,type) 的默认 `sort = max+1`；新增纯函数 `metaDiscriminatorField` / `nextSortValue` + DB 薄层 `maxMetaSort`。
- `server/mongod/reorder.go`（新增）：四个 `Reorder*` 仓储方法、纯校验函数 `computeReorderAssignments`、sentinel error、DB 薄层 `reorderMeta`。
- `server/server/handler/catalog/reorder.go`（新增）：四个 reorder handler，经窄接口 `metaReorderer` 断言取得仓储能力。
- `server/server/handler/handler.go`：`AppHandler` 接口 + `appHandler` 转发四个 Reorder。
- `server/server/server.go`：注册 `POST /{channel,platform,arch,app}/reorder`。
- `server/server/model/model_test.go`：四个 JSON 契约 want 追加 `Sort`。

> 关键决策：`Reorder*` **刻意不并入** `mongod.AppRepository` 大接口，仅作为具体 `*appRepository` 能力，由 catalog 窄接口 `metaReorderer` 断言获取。这样 TUF bootstrap 的测试 mock 无需被动新增方法即可继续满足 `AppRepository`，**零 TUF 文件改动**。

### Dashboard
- `packages/shared/src/index.ts`：`AppSummary`/`Channel`/`Platform`/`Architecture` 各加 `Sort: number`。
- 依赖：`@dnd-kit/core` / `@dnd-kit/sortable` / `@dnd-kit/utilities`。
- `apps/web/src/shared/components/common/sortable-list.tsx`（新增）：基于 dnd-kit 的可复用排序原语（无障碍交给 dnd-kit）。
- `apps/web/src/shared/lib/reorder.ts`（新增）：`reorderById` 纯函数。
- `features/{channels,platforms,architectures,apps}/{api.ts,hooks.ts}`：各加 `reorder(ids)` 与 `useReorder*Mutation`（乐观更新 + 回滚 + invalidate）。
- 四个列表 UI 接入拖拽手柄；搜索/过滤激活时禁用拖拽，避免对子集重排。apps 落在 list 视图，card/board 按 `Sort` 显示默认序。
- `apps/web/src/features/channels/hooks.test.tsx`（新增）：reorder hook 乐观更新/回滚单测。
- `dashboard-next/.gitignore`：补 `.omc/`（与根仓库策略一致，避免 OMC 运行态产物被 `eslint .` 纳入）。

## 验收标准

1. 四模型有 `Sort` 字段且对外 JSON 暴露 `Sort`；契约测试同步。
2. 四列表读取按 `sort` 升序；老数据维持创建顺序。
3. 新建实体默认追加到该 owner+type 末尾。
4. 每类 reorder 端点按 (owner,type) 全量重写，拒绝外来/未知/非法/重复 id，复用 Edit 权限。
5. 前端四列表可拖拽排序，乐观更新 + 失败回滚，搜索时禁用。
6. 视觉值走 DESIGN.md token，无新增 hex/arbitrary；文案 brand-neutral；不碰 TUF。

## 验证缺口（需 vm-node02 / 有 mongo 环境验证）

- 根包 E2E `faynoSync_test.go` 与所有依赖 live mongo 的路径（`maxMetaSort` / `reorderMeta` / `resolveOwnerScope` 的真实读写、`listItems` 新排序对四列表的实际效果、老文档靠 `_id` tiebreaker 维持创建顺序）本地无法验证。
- 载荷假设「Mongo 升序中 null/缺失 < 数字」需在 staging 实测确认。
- 拖拽交互的浏览器端到端（真实数据 + 后端）未做冒烟。

## 已知边界（非阻塞）

- 元数据列表服务端固定 cap 100（既有限制）；某 owner 资源 > 100 时列表与 reorder 仅覆盖前 100，其余 `sort` 不变。
- team-user 若仅可见其 `Allowed` 子集，对子集 reorder 会与 admin 其它同类资源的 sort 交错；建议后续按需收紧（如 reorder 限 admin 或按 Allowed 校验完整集合）。
- create 默认 `sort = max+1` 在并发创建下有极小竞态，`_id` tiebreaker 保证确定顺序，低频管理操作可接受。
- reorder 对 `len(ids) <= 1` 直接 no-op：单元素请求即便含非法 hex 或外来 id 也返回 200（跳过输入校验），对数据无害仅 API 契约略松。
- `asReorderer` 为每请求运行时断言（失败 500）；功能正确，可后续优化为 `NewAppHandler` 构造期一次性断言（fail-fast）。
