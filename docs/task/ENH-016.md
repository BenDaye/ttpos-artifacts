# ENH-016 MCP server 增加 SSE/HTTP 形态(双模)并部署到 vm-node02

## 背景与目标

`@ttpos/mcp`(ENH-015)目前只有 **stdio** 形态。本期把它扩成**网络形态**,让远程 agent 经 HTTP 接入,
并部署到 vm-node02、经 Caddy 反代对外。

## 决策(已确认)

- **传输实现:Streamable HTTP**(`WebStandardStreamableHTTPServerTransport` + `Bun.serve`)。
  它是 MCP 规范里 **SSE 的现代继任**(GET 端点默认以 SSE 流推送、POST 收消息),Web 标准 Request/Response、
  Bun 原生、零额外依赖、非 deprecated。**不**用 legacy `SSEServerTransport`(已 @deprecated 且基于 Node http,Bun 里要引 express)。
- **双模:保留 stdio + 新增 HTTP**,用 `MCP_TRANSPORT=stdio|http` 选择,**默认 stdio**(不破坏现有本地接入)。
- **部署目标:远程/共享**——部署到 vm-node02,经**现有 API 域名 `update.ttpos.dev/mcp` 路径**反代(不另起子域名、无新 DNS),与 api/dashboard 同列。

## 硬边界

- HTTP 形态网络可达 → **强制 bearer 鉴权**:客户端须带 `Authorization: Bearer <MCP_HTTP_AUTH_TOKEN>`;HTTP 模式下未配置该 token 即启动失败。
- **Origin/Host 校验**(DNS-rebinding 防护,本地 MCP HTTP 的头号攻击面):校验 `Host`/`Origin` 白名单,不符 403。
  注:SDK 的 `hostHeaderValidation` 中间件是 express 形态、**不适配** Bun.serve,故在 `fetch` 处理器里自实现轻量校验。
- 上游 FaynoSync token(`API_TOKEN`,fns_)仍只走**服务端 env**;与 MCP 层 bearer 是**两个独立 token**(client→MCP、MCP→FaynoSync)。
- 只读工具面不变;brand-neutral(server 名/工具名/路径中性);**不碰 TUF**。
- 无状态 session(`sessionIdGenerator: undefined`,只读够用);端点 `/mcp`;另设免鉴权 `/healthz` 供 compose/Caddy 探活。

## 技术事实(已核对已装 SDK 1.29)

- `WebStandardStreamableHTTPServerTransport.handleRequest(req: Request): Promise<Response>`,文档明确支持 **Bun**;
  无状态用 `sessionIdGenerator: undefined`,`enableJsonResponse` 默认 false(优先 SSE 流)。
- 客户端测试用 `StreamableHTTPClientTransport`(SDK client 子模块)。
- **生命周期待实现时以 SDK 示例核实**(无状态:`server.connect(transport)` 一次 + 每请求 `handleRequest`,或每请求新建——以官方示例为准,避免 per-request 误接)。

## 实现说明(已落地)

- **生命周期(实测纠偏)**:无状态模式下 SDK **强制每请求新建 transport**(复用抛 `Stateless transport cannot be reused`)。
  `http.ts` 的 `handleMcpRequest` 每请求新建 `McpServer`+transport、connect、handleRequest(注册 9 工具开销极低)。
- **请求顺序**:`/healthz`(免鉴权)→ Origin/Host 校验 → 路径 → bearer → MCP。bearer 在任何 per-request 构建之前,DoS 友好。
- **鉴权**:`MCP_HTTP_AUTH_TOKEN` http 模式必填(缺则启动失败);`isBearerValid` 用 timing-safe 比较(先判长度再 `crypto.timingSafeEqual`)、严格匹配 `Bearer <token>`。
- **Origin/Host**:`isOriginAllowed` —— 无 Origin 放行(非浏览器)、有 Origin 不在白名单则 403、Host 白名单仅配置时启用。挡浏览器 DNS-rebinding。
- **流式存活(评审修复)**:Bun 默认 `idleTimeout` 10s 会在上游慢调用时掐断 SSE 响应;对 `/mcp` 调 `server.timeout(req, ceil(timeoutMs/1000)+15)`(~30s)。另加 `Bun.serve` `error` 回调(stderr 日志 + 脱敏 500)。
- **两个独立凭据**:`MCP_HTTP_AUTH_TOKEN`(client→MCP)与 `API_TOKEN`(MCP→FaynoSync,fns_);上游 token 只在服务端 env。
- **dashboard Dockerfile 连带修复**:补 `COPY apps/mcp/package.json`——ENH-015 加 mcp workspace 后,旧 Dockerfile 缺该 manifest 会让 `--frozen-lockfile` 失败(下次发版才触发)。已用 /tmp 模拟证实「缺则失败、补则通过」。

## 安全闸门(上线前必做)

- **`API_TOKEN` 必须用只读 team-user 签发,绝不用 admin**。FaynoSync 的 admin token 是全量读写删;MCP 层虽只读,但它转发的上游 token 权限不受 MCP 约束——bearer 一旦泄露即等同该上游 token 权限。
  上线前用 `whoami` 工具确认该 token 身份(应为受限 team-user,非 admin)。
- 后续可选硬化(非阻塞):Caddy `rate_limit` 限速(LOW-1 DoS)、给 SDK transport 也开 `enableDnsRebindingProtection` 做冗余。

## Stage 2 部署执行(待外部就绪 — runbook)

1. 合并本 PR → 打 `mcp-v<ver>` tag → CI(build-mcp.yaml)产出 `ghcr.io/bendaye/ttpos-artifacts/faynosync-mcp:latest`。
2. **DNS**:无需新增——复用已解析的 `update.ttpos.dev`。
3. **host Caddy**:在 `/opt/caddy/Caddyfile` 的 `update.ttpos.dev` 块内加 `handle /mcp* { reverse_proxy faynosync-mcp:3010 { flush_interval -1 } }`(放在 API 反代之前),`caddy reload`。
4. **host .env**:在 `/home/ubuntu/ttpos-releases/.env` 填 `MCP_HTTP_AUTH_TOKEN`(高熵随机)与只读 `API_TOKEN`。
5. **host compose**:同步 `deploy/docker-compose.yml` 的 mcp service → `docker compose pull mcp && docker compose up -d mcp`。
6. **冒烟**:对 `https://update.ttpos.dev/mcp` —— 无 bearer→401;非法 Origin→403;带 bearer 用 MCP client 列工具 + `whoami` 校验 token 为只读身份(`/healthz` 仅容器内部探活,不经 Caddy 暴露)。
