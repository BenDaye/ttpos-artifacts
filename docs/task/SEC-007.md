## 描述

零信任审计修复（已合入 main，提交 `ffa0129` / PR #8）为 `server/server/model/model.go` 的多数字段补齐了显式 `json` tag 以锁定 wire 格式，但有意保留以下内部字段以默认字段名序列化进 API 响应，并标注 `// TODO: 收紧为 json:"-"（改 wire，本批不实施）`：

- `App.Private`（model.go:25）
- `App.Owner`（model.go:28）
- `Channel.Owner`（model.go:73）
- `Platform.Owner`（model.go:81）
- `Arch.Owner`（model.go:88）

`Owner`（内部用户名）与 `Private`（可见性意图）属于不应直接对客户端暴露的内部字段，正是零信任审计会标记的"响应中泄露内部信息"。该暴露为既有行为（改动前 struct 完全无 json tag，本就全字段暴露），上一批为避免破坏 wire 契约仅锁定格式、留作 TODO，未实际收紧。本任务负责评估并完成收紧。

验收标准：
1. 调查前端 shared 类型、Dashboard 调用方与测试是否实际依赖上述 `Owner` / `Private` 字段；无依赖则改为 `json:"-"`，有依赖则改为最小必要暴露或脱敏后再暴露。
2. `model.go` 移除上述 5 处遗留 TODO，对应字段不再以默认名进入 API 响应。
3. 若改动 wire 格式，同步前端 shared 类型、调用、相关测试与文案，避免破坏既有兼容契约。
4. 后端 `go test ./...`（完整 stack）与前端 `typecheck` / `lint` / 相关 `test` 通过。

## 调查结论（investigate，2026-06-01）

结论：5 处字段改 `json:"-"` 安全且能达成收紧目标。三条关键因果链已逐一查实——

1. **输出有效性（改 `json:"-"` 确实能移除响应字段）**：4 个 list 端点均为
   `c.JSON(http.StatusOK, gin.H{"apps": &appsList})`，`appsList` 类型是 `[]*model.App`
   （Channel/Platform/Arch 同理），见 `server/server/handler/catalog/list.go:34/56/78/100`。
   `c.JSON` 用 `encoding/json` 直接 marshal 这些 struct，所以 model 上的 json tag 控制 wire 格式。
   当前响应键是大写 `"Owner"`，正是 `encoding/json` 对「导出且无 json tag」字段的默认行为，
   印证字段确由 struct 序列化产生，改 `json:"-"` 后即从响应消失。
2. **输入安全（改 `json:"-"` 不破坏入库/请求解析）**：
   - `Private` 创建走 `c.PostForm("data")` → `params["private"]` → `utils.GetBoolParam`
     → 作为函数参数传入 `CreateApp(...)`（`create.go:111/113`），mongo 文档由
     `bson.E{Key:"private"}` 手工构建（`mongod/create.go:224`），从不经 `model.App` 的 JSON 绑定。
   - `Owner` 由服务端鉴权上下文赋值（`owner = teamUser.Owner` / 用户名），经 `bson:"owner"` 写库，
     同样不经请求 JSON 绑定到 `model.App`。
   - Mongo 读写由 `bson` tag 决定，与 `json` tag 完全独立；故 `json:"-"` 只改 API 响应 wire，
     不影响入库、查询、权限过滤（`owner` 过滤用的是 bson 字段）。
3. **依赖面（谁还在读这些字段）**：
   - 前端：`dashboard-next` 对响应字段 `Owner` / `Private` **零依赖**。`@ttpos/shared` 的
     `AppSummary` / `Channel` / `Platform` / `Architecture` 类型本就不含这两个字段；
     `apps.json` 的 `form.private` 与 `app-form-dialog.tsx` 的 `form.private` 是**创建/更新请求侧**
     的表单 label（发送 `private`），不读响应，不受影响。
   - 后端测试：仅 4 个 list 测试断言响应里的 `Owner`（详见下方方案），`Private` 无任何测试断言。
     其余 `owner`/`private` 出现均为请求 payload（如 `:571`）或 bson 种子数据（如 `:2732`、`:2808`），属输入侧。

附带说明：`SpecificApp.Owner`（model.go:45）无 json tag 但本任务未标 TODO，且其所在响应路径未被本次断言覆盖；
按任务约定不在本批范围，保留现状，后续可单列任务评估。

### 改动 2：`server/faynoSync_test.go`（4 个 list 测试改为断言「不再暴露」）

四处当前断言形如 `assert.Equal(t, expected.Owner, actual....Owner)`（期望 `"admin"`），
收紧后响应不再含 Owner，反序列化得空串。改法（每处一致）：

- 保留本地反序列化 struct 中的 `Owner string `json:"Owner"`` 字段（用于探测服务端是否仍下发）。
- 删除 `expected` 字面量里的 `Owner: "admin",` 行（其余字段不动）。
- 把相等断言替换为非暴露断言：

```go
// TestListAppsUsingTeamUser，原 server/faynoSync_test.go:6708
assert.Empty(t, actual.Apps[i].Owner, "Owner 不应出现在 API 响应中 (SEC-007)")

// TestListChannelsUsingTeamUser，原 :6849 附近

// TestListPlatformsUsingTeamUser，原 :6989 附近

// TestListArchsUsingTeamUser，原 :7129 附近

```

`assert` 已在该文件导入，无需新增 import；`expected` 仍用于各自的 Name 断言，故保留变量。
