# BUG-015 修复 FaynoSync CI 重传覆盖失败

- **status**: completed
- **priority**: P1
- **owner**: Codex
- **createdAt**: 2026-06-24 08:16

## 描述

GitHub Actions 上传到 FaynoSync 时会出现 `HTTP 500`：

```text
app with this name, version, platform, architecture and extension already exists
```

但对象存储里的文件已经被替换。需要修复 CI 与 FaynoSync 上传语义，使普通上传、重复上传和强制覆盖的结果可预期。

验收标准：

1. `faynosync=on` 不再把 `/checkVersion` 当作存在性查询；同 app/version/channel/platform/arch/extension 已存在时，构建前 `/upload/check` 先返回 409，最终 `/upload` 仍可靠返回 409。
2. `faynosync=force` 只能由具备 `apps.edit` 的身份覆盖已有版本；`FAYNOSYNC_TOKEN` 若没有该权限会在构建前预检查 403。
3. `/upload` 遇到重复 artifact 时不会先覆盖对象存储再返回错误。
4. Android、Windows、macOS、iOS workflow 的 FaynoSync 行为一致。

## 完成情况

已按 PLAN-031 完成服务端语义、测试、workflow 与验证四条线。`faynosync=force` 现在通过 `/upload` + `overwrite=true` 覆盖，但 overwrite 额外要求 `apps.edit`；`FAYNOSYNC_TOKEN` 权限不足时会在构建前预检查失败。普通重复上传在对象存储写入前返回 409；workflow 在构建前用 `/upload/check` 做无副作用预检查。

## 笔记

- 2026-06-24 08:16：根因初判为两层问题叠加：workflow 使用 `/checkVersion` 作为版本存在性判断，但该接口只回答“是否有更新版本”，且只查询 `published=true`；服务端 `/upload` 在重复检查前已经把文件写入对象存储，导致桶文件被覆盖后 Mongo 写入失败。
- 2026-06-24 08:16：系统化复核修正：CI `force` 不能简单改为 `/apps/update`，因为该接口要求版本 ObjectID 且权限面更宽。更合理的修复边界是把覆盖语义收敛在 `/upload overwrite=true`，由服务端额外校验 `apps.edit`，并让普通重复上传在对象写入前返回 409。
- 2026-06-24 08:57：PLAN-031 已经通过 ralplan 审核，执行期使用 `.omx/ultragoal/goals.json` 持久追踪。
- 2026-06-24 09:10：执行期收敛为 `/upload` 唯一正确性边界；不引入 `/search` 预检查，避免扩大 API token 读权限依赖。
- 2026-06-24 09:25：最终 review 发现只读 preflight 不能挡并发 loser 写对象存储，已改为在写存储前先写入内部 `upload_claims` tuple claim；拿不到 claim 的请求直接 409。
