# BUG-022 Keep build status across private routes

- **status**: completed
- **priority**: P1
- **owner**: codex
- **createdAt**: 2026-07-10
- **plan**: PLAN-042

## Problem

The Dashboard build status sheet is currently owned by `ApplicationsPage`. After a QA or PM user triggers a test build, leaving `/applications` unmounts the page and drops the active build state and polling observer. This makes the global "Build Test Package" workflow feel fragile: users can start a long-running build but lose the in-product progress surface when they navigate to app detail or another private route.

## User-visible acceptance

- After triggering a build from `/applications`, navigating to another private route keeps a build status entry available.
- The user can reopen the status sheet outside `/applications` and still see targets, platform, and the Actions run link.
- The active build is session-restorable for a bounded time window and is cleared after timeout or sign-out.
- The implementation does not change server APIs, workflow behavior, build trigger contracts, branch policy, permissions, rate limits, or completion polling semantics.

## Notes

This follows the residual risk from PLAN-041. The fix should move ownership to a private-shell/global build activity layer while keeping `/applications` as the build trigger entry.

## Result

Implemented a private-shell build activity owner. `/applications` still owns only the trigger dialog; the active build status is available across private routes, survives refresh via bounded `sessionStorage`, and is cleared on sign-out.
