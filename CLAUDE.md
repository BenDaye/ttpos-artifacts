## Project Overview

This repository (`ttpos-artifacts`) is a monorepo that contains:

1. **FaynoSync Server** (`server/`) — Go-based update distribution API (forked from [ku9nov/faynoSync](https://github.com/ku9nov/faynoSync), independently maintained).
2. **FaynoSync Dashboard** (`dashboard-next/`) — Production frontend: React 19 SPA managing app versions, artifacts, channels, platforms, telemetry, and team users. Built with Bun workspaces, Vite 8, TanStack Router, Tailwind v4, and shadcn/ui (Base UI).
3. **Legacy Dashboard** (`dashboard/`) — React 18 + Yarn 4 SPA, retained as a rollback anchor only. Not built from `main`; do not add new features here.
4. **TTPOS Build Workflows** (`.github/workflows/`) — GitHub Actions CI/CD pipelines that build the TTPOS Flutter POS applications (Android/Windows/macOS/iOS/Web) from the private repo `innet8/ttpos-flutter`.

## Build & Dev Commands

### Dashboard (`dashboard-next/`)

```bash
cd dashboard-next
bun install --frozen-lockfile   # Install dependencies (Bun workspaces)
bun dev                         # Vite dev server on port 3000 (apps/web)
bun run build                   # tsr generate + tsc --noEmit + vite build
bun run typecheck               # tsr generate + tsc --noEmit
bun run lint                    # ESLint flat config (@antfu/eslint-config)
bun run lint:fix                # ESLint --fix
bun run test                    # Vitest 4 unit tests
bun run test:e2e                # Playwright e2e (preview server on :4173)
bun run preview                 # Preview production build locally
```

Run from the monorepo root (`dashboard-next/`); scripts dispatch to `apps/web/` via `bun --filter`.

### Legacy Dashboard (`dashboard/`)

Retained as rollback anchor only. Use Yarn 4 + Node 20 if a hotfix on the legacy image is required; otherwise leave it untouched.

### Server (`server/`)

```bash
cd server
go build -o faynoSync .     # Build server binary
go test ./...               # Run tests
```

### Deploy (`deploy/`)

```bash
cd deploy
docker compose up -d        # Start all services
docker compose build        # Build images locally
```

## Architecture Patterns

### Authentication Flow
- JWT stored in `localStorage` (key: `token`, see `STORAGE_KEYS` in `packages/shared`)
- `features/auth/auth-store.ts` exposes `isAuthenticated()` and login/logout helpers
- `shared/lib/http.ts` attaches `Authorization: Bearer <token>` header and on 401 clears the token and `window.location.href = '/signin'`
- TanStack Router `_private.tsx` guard redirects unauthenticated users; `_public.tsx` redirects authenticated users away from auth pages

### Data Fetching (React Query)
- All API calls live in `features/<domain>/api.ts` and are wrapped by hooks in `features/<domain>/hooks.ts`
- Pattern: `useQuery` for reads, `useMutation` with `onSuccess` → `queryClient.invalidateQueries()`
- Hierarchical query keys e.g. `['app-search', appName, params]`, `['apps', 'list', params]`
- Multi-select filters for versions / telemetry are passed as repeated query params; single-value filters route through the server `/search` API, multi-value falls back to client-side filtering

### Styling System
- Tailwind v4 `@theme` directive with OKLCH color tokens (light + dark)
- Theme is toggled by `ThemeProvider` (system / light / dark)
- Components use `cn()` (`shared/lib/utils.ts`) to merge Tailwind classes; never hardcode hex colors
- shadcn/ui `base-nova` style on top of `@base-ui-components/react` primitives — the Dialog renders two Close affordances (footer button + absolute X), this is intentional

### Dashboard View Modes
- Three interchangeable layouts: **Card** (grid), **List** (dense table), **Board** (kanban by channel)
- Persisted via `useUiStore` (Zustand) under localStorage key `layoutPreference`
- Toggled via `LayoutSwitcher` (`shared/components/layout-switcher.tsx`)

### Dialog/Form System
- `shared/components/common/entity-form-dialog.tsx` — generic create/edit dialog (default submit label "Save")
- `shared/components/common/confirm-dialog.tsx` — destructive confirmation
- `shared/components/common/changelog-modal.tsx` — react-markdown rendering with array fallback per version
- `features/apps/components/{add-artifact,download-artifacts,upload-version,version-edit,app-form}-dialog.tsx` — domain-specific dialogs

### TUF (currently disabled)
- Settings sidebar hides the TUF tab; `/settings/tuf` route renders a stopped placeholder
- `features/tuf/scripts/*` (Bootstrap / RotateRootKeys / SignMetadata / GenerateSignatures / history utils) are retained as pure functions for future R4 reactivation

## Docker Deployment

- **Multi-stage build**: `oven/bun:1.3.13-alpine` (build) → `nginx:alpine` (serve)
- **Runtime env injection**: `VITE_API_URL` compiled as placeholder `__VITE_API_URL_PLACEHOLDER__` and replaced at container startup via `apps/web/docker-entrypoint.sh` (`sed` over `/usr/share/nginx/html/assets/*.js`)
- **Nginx (`apps/web/nginx.conf`)**: Port 3000, SPA fallback (`try_files`), 1-year immutable asset cache, uncached `index.html`, security headers (CSP, X-Frame-Options, Referrer-Policy, Permissions-Policy)
- **Image**: `ghcr.io/<owner>/ttpos-artifacts/faynosync-dashboard-next`
- Legacy `dashboard/` image (`faynosync-dashboard`) is still buildable for rollback via `build-dashboard.yaml` workflow_dispatch

## Project Development

Use `/pma` for task management. Tasks and plans live in `docs/task/` and `docs/plan/` (git-tracked, portable across environments).

### PMA Three-Phase Workflow

All feature/bug/refactor work follows a strict gate-based flow:
1. **Investigation** — trace code, search context, create/claim task in `docs/task/`
2. **Proposal** — output current state + proposal + risks + scope, wait for user approval
3. **Implement** — only after explicit `proceed`; dispatch via Kanban workspace if available, otherwise implement locally

**Do not skip phases.** Do not implement before approval.

### Vibe Kanban MCP Integration (Pluggable)

Vibe Kanban MCP is an optional but preferred integration for issue tracking and workspace dispatch. It is **auto-detected** at session start via `get_context()`.

**Issue-First workflow** (when MCP is available):
```
list_organizations() → list_projects(org_id) → create_issue(project_id, title, desc, priority)
  → start_workspace(issue_id, executor, repositories) → [auto: issue moves to "In Progress"]
    → get_execution() / create_session(executor: "CLAUDE_CODE") + run_session_prompt()
      → update_issue(status: "Done") → update_workspace(archived: true)
```

Core rules:
- Files (`docs/task/`, `docs/plan/`) are **always** the primary data source — Kanban is the sync target
- Issue is the entry point: create Issue first, then create Workspace from Issue (not the reverse)
- Creating a workspace linked to an issue **automatically** moves the issue to `In Progress`
- `link_workspace_issue()` also triggers the same auto `In Progress` transition
- `project_id` must be passed explicitly to `create_issue()` and `list_issues()`
- If `get_context()` returns `project_id: null`, discover it via `list_organizations()` → `list_projects()`
- When MCP is unavailable, continue with file-only workflow — no errors, no warnings

Critical constraints (verified by E2E testing):
- `start_workspace` requires either `issue_id` or `prompt` — omitting both returns HTTP 400
- `create_session` must specify `executor: "CLAUDE_CODE"` explicitly — the default is unreliable
- Sub-issues are status-independent: completing all children does NOT auto-complete the parent
- Use `update_workspace(archived: true)` instead of `delete_workspace()` — delete fails with 409 if sessions exist
- `remove_issue_tag()` and `unassign_issue()` take junction IDs, not entity IDs

Full tool mapping, status/priority mapping, constraint details, and dispatch protocol are defined in the PMA skill (`/pma`).
